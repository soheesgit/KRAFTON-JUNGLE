## Challenge 02 — Stack Buffer Overflow

프로그램을 실행하면 파스칼 삼각형은 정상적으로 출력되지만 마지막에 다음 오류가 발생했다.

```text
*** stack smashing detected ***: terminated
Program received signal SIGABRT
```

`bt`로 호출 스택을 확인했다.

```gdb
(gdb) bt
#5  __stack_chk_fail ()
#6  main () at challenges/02_stack_buffer_overflow/bug.c:112
```

`#0 ~ #5`는 libc 내부의 오류 처리 함수이고, `#6`에서 내가 작성한 `main()`이 나온다.  
특히 `__stack_chk_fail()`이 호출된 것을 보고 **스택 카나리가 손상되었다**고 추측할 수 있었다.

참고로 처음 보인 `0x0000fffff7e774d8`은 libc 내부에서 프로그램이 멈춘 현재 명령어 주소일 뿐, 그 주소 자체가 버그의 원인은 아니다.

### 배열 확인

`tri`의 크기는 `SIZE = 105`이므로 정상적인 인덱스는 `0 ~ 104`이다.

그런데 배열 밖을 확인해 보니:

```gdb
(gdb) p tri[105]
$4 = 1
(gdb) p tri[106]
$6 = 14
(gdb) p tri[107]
$7 = 91
```

`105` 이후에서도 `1, 14, 91 ...`처럼 파스칼 삼각형의 다음 행 값이 발견되었다.

즉, 배열 밖까지 값이 실제로 쓰였다는 뜻이다.

코드를 확인해 보니 원인은 다음 반복문이었다.

```c
for (int i = 0; i <= rows; i++)
```

`ROWS`가 14라면 필요한 행은 `0 ~ 13`인데, `<=` 때문에 `i = 14`까지 실행된다.

14번째 행의 첫 번째 인덱스는:

```text
14 * 15 / 2 = 105
```

이므로 바로 `tri[105]`부터 배열 범위를 벗어난다.

따라서 다음과 같이 수정했다.

```c
for (int i = 0; i < rows; i++)
```

수정 후에는 `stack smashing detected` 없이 정상 종료되었다.

## Thinking Point

왜 배열을 넘어 쓰는 순간이 아니라 `return 0;` 근처에서 오류가 발생했을까?

컴파일러는 스택의 중요한 영역이 덮어써지는 것을 감지하기 위해 **스택 카나리(stack canary)** 값을 저장해 둘 수 있다.

배열 범위를 넘어 쓰면서 이 카나리까지 손상되었고, 함수가 종료되기 직전에 원래 값과 비교했을 때 값이 달라져 `__stack_chk_fail()`이 호출된 것이다.

```text
배열 범위 초과 write
→ 주변 스택 메모리 손상
→ stack canary 손상
→ 함수 종료 직전 검사
→ __stack_chk_fail()
→ SIGABRT
```

카나리까지 손상되지 않는 작은 오버플로라면 `stack smashing detected`가 발생하지 않을 수도 있다.

하지만 오류가 없다는 뜻은 아니다. 이미 배열 밖의 메모리를 건드린 것이므로 **Undefined Behavior**이고, 다른 지역변수가 망가지거나 나중에 전혀 다른 위치에서 크래시할 수도 있다.

단, 이 메모리 손상이 다른 프로그램의 메모리를 직접 망가뜨리는 것은 아니다. 일반적인 운영체제에서는 프로세스마다 가상 메모리가 분리되어 있기 때문이다.
